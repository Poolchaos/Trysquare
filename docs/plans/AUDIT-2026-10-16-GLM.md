## 1. Method and evidence

Everything below was verified on this machine on 2026-10-16 unless a document
is cited as its source. Machine: Windows 11 (10.0.26200), Node v22.17.0,
npm 10.9.2, git 2.50.0.windows.1, repository at commit df94bb0 with a clean
working tree. The `claude` CLI is not on PATH here (`Get-Command claude`

assumed. The project's own records were last verified 2026-08-18 on Linux
(PROJECT-STATE.md); this audit re-verified those records against the live
tree instead of trusting them.

"Ran" means a command was executed here and its output read. Files cited as
`path:line` were read at that line. What this audit did not cover is listed
in section 12.

## 2. Executive summary

The construction work is done and the project's records about that are
accurate: nine screens, 34 API route files, 47 unit test files, three e2e
specs, and every work package in M4-FINISH-PLAN and DASHBOARD-SHELL-PLAN

only, and none of its verification runs on this Windows machine. The unit

paths rejected as project URLs) and one security exposure (next.js
advisories, section 6) stand on their own regardless of platform.

## 4. Unit failure taxonomy on Windows (732 tests, measured)

Five distinct root causes. Counts are from the vitest run above.

1. **Product bug: Windows absolute paths rejected as git URLs.**
   `src/lib/git/url.ts:57` accepts local paths only when they start with
   `/`, `./` or `../`, so `C:\...` throws. 10 suites fail at fixture setup
   (`InvalidGitUrlError` out of `cloneBare`), and in the product a user
   cannot add a local project by absolute path on Windows at all.
2. **`spawn EFTYPE` for the fake CLI.** `tests/fixtures/fake-claude.mjs`
   relies on its shebang and is spawned directly (`src/server/engine/headless.ts:101`,
   `probe.ts:49`); Windows refuses. About 52 tests across four files. The
   same code path means a real CLI installed as an npm `.cmd` shim would
   also fail to spawn; a native `.exe` would not.
3. **EBUSY cleanup.** `tests/server/db/helpers.ts:24` deletes temp
   directories while the better-sqlite3 handle is open (no `db.close()`).
   Windows cannot unlink open files; about 197 tests whose bodies passed are
   marked failed by their own cleanup.
4. **POSIX literals in `tests/lib/paths.test.ts`.** Seven tests expect
   forward slashes; `src/lib/paths.ts` itself is correct for the platform it
   runs on.
5. **Mode-only diff fixture.** Four tests in `tests/lib/git/diff.test.ts`
   depend on the executable bit, which Windows git does not track. Not
   CRLF-related: the LF/CRLF warnings in the log correspond to zero
   failures.

## 5. Windows portability findings beyond the suite

- **The free demo is broken here.** `scripts/demo-fixture.ts:115` passes a
  raw absolute path to `cloneBare` (cause 1), `:149` and `:155` build
  `file://` URLs from backslash paths, and `:121` points the engine at the
  fake `.mjs` (cause 2). `npm run demo:fixture -- --fake` cannot run on this
  machine.
- **e2e cannot pass here.** The journey fills a `file://${path}` URL
  (`e2e/journey.spec.ts:43`, malformed with backslashes), and every stage
  call spawns the fake `.mjs` (cause 2). Additionally `e2e/setup.ts:51`
  deletes the data directory its own already-started server has opened:
  Linux unlinks it silently and runs on, Windows refuses with EBUSY.
- **System prompt rides in argv.** `src/lib/engine/command.ts:62-64` passes
  `--system-prompt` on the command line (only the user prompt moved to
  stdin). Windows caps a command line at 32,767 characters. Measured with
  the repo's own composer: the sample protocol's S3 system prompt is 15,093
  characters (15 rules, 18 directives), which fits; a larger real protocol
  need not.
- **The credential helper is dropped.** `src/server/gitops/run.ts:51` sets
  `GIT_CONFIG_NOSYSTEM=1`; on this machine `credential.helper=manager` lives
  in the system config (`git config --system --list`, measured), so
  private HTTPS clones have no helper.
- **Mode B launch command is POSIX-only.** `src/server/engine/interactive.ts:97`
  emits `cd ... && claude ... "$(cat ...)"`.
- **Minor:** `scripts/check-style.mjs:120` splits a `relative()` path on
  `/`, so the `review/` JSON exemption misbehaves on backslash paths (the
  directory does not exist on this machine, so the gate is unaffected here).
- **Default data dir** resolves to `C:\Users\<user>\.local\share\trysquare`
  via `join`; unusual for Windows but functional.

## 6. Security findings (verified)

- **next.js advisories.** `npm audit`, run 2026-10-16: 13 vulnerabilities
  (1 critical, 10 high, 2 moderate). The installed `next` is 16.2.12 and the
  critical advisory's affected range ends at 16.3.7. PROJECT-STATE.md:133
  still records "0 vulnerabilities" (measured 2026-08-03, 586 dependencies);
  the re-check trigger has effectively fired. Whether the critical applies
  to this app's exposure (local, `next start` without a hostname) is the
  maintainer's call, but the record is stale either way.
- **No origin or host checking.** Verified structurally: there is no
  middleware, no Host or Origin check anywhere in `src`, and `next.config.ts`
  contains only `serverExternalPackages`. `next start` binds all interfaces
  by default. The parallel audit reports driving a cross-origin `text/plain`
  POST that was processed (a 400 from URL validation, not a CORS block),
  which this session did not independently repeat; the structure is
  consistent with that result. For a local single-user app with no auth, any
  website the user visits can attempt state-changing POSTs while the server
  runs.

- Minor overstatements: the G3 screenshot set predates only the newest

## 11. Claude connect: current state and the minimal feature

What exists, verified: `claude auth status` is parsed read-only
(`probe.ts:86-118`) and surfaced by `GET /api/auth` to a manual
"Check sign-in" button on Settings that distinguishes subscription from
per-token billing; model probes gate the picker; `TRYSQUARE_CLAUDE_PATH`
is environment-only (the settings table accepts exactly three numeric
keys). There is no saved path, no login action, and no auth check before a
review starts, so an unconfigured machine reports "Not signed in" for
reasons that have nothing to do with signing in (a missing binary and a
missing login are the same answer to the user).

Minimal connect feature, agreeing with the parallel audit: resolve the
binary (env var, then a saved setting, then PATH; on Windows accept only an
`.exe`), validate it with `--version` and show the version, give
"CLI not found" its own state with the real error, add the path to the
settings screen, and when signed out show the exact `auth login` command
for the user to run in their own terminal. Do not store a setup token
(contradicts SECURITY.md's no-credential stance, and the env scrub would
strip the variable it rides on anyway). Whether a login flow can be driven
from the server at all cannot be verified without the CLI installed.
Per the charter this sits behind the active gate and belongs in the idea
inbox or a new gate, and it needs a DECISIONS entry.

## 12. Not covered by this audit

Pipeline invariant fuzzing, quotation-check adversarial cases, state-machine
race conditions, SSE subscriber leaks, migration correctness, and hostile
git inputs (branch names, submodules, LFS, long paths). The parallel audit
stopped the same areas for the same reason. A focused pass on those is
still owed. Nothing in this audit was fixed; every finding above is
reported, not repaired.
